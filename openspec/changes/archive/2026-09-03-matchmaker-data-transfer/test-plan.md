# Test Plan — matchmaker-data-transfer

> **紅燈形式的事前聲明**：本 change 的六個 `lib/` 模組（`transfer-types.ts`、`backup.ts`、
> `csv.ts`、`history-csv.ts`、`roster-csv.ts`、`transfer-storage.ts`）**全部是新檔案**，
> 每個模組第一個測試的紅燈形式會是「模組／函式尚不存在」的解析失敗，之後同檔追加的測試
> 才是斷言失敗型紅燈。兩者都算真紅燈。
>
> 依 root `CLAUDE.md`「紅燈要是真的」：若實作到後段出現「加入測試即綠」的情況
> （既有保證透過新入口重新曝光），MUST 在 tasks.md 誠實標註為 regression guard，
> **SHALL NOT 用 mutation check（改斷言看紅再改回）偽造紅燈**。此時測試的有效性改由
> mutation 驗證（改壞看紅、還原看綠）承擔，並記錄於 tasks.md，比照 M2 §14 的做法。
>
> **Tier 說明**：`lib/` 下的純函式為 `unit`（Vitest + happy-dom）；
> 頁面路由與 `components/matchmaker/**` 依 `nextjs-pickball/CLAUDE.md` 屬**例外層**
> （純入口／純視覺，不強制單元 TDD），以 `e2e`（Playwright）驗收。
> 本 change **無 `integration` 層**——沒有跨前後端的行為，`/api/*` 完全不參與。

## 驗證檢查

- **每個 Requirement 至少一個測試**：8 個 Requirement，皆有 ≥ 2 列。
- **每個 Scenario 至少一個測試**：38 個 Scenario ↔ 38 列，一對一對應，無遺漏、無合併。
- **每列都有 Tier**：是。unit 30 列、e2e 8 列、integration 0 列（本 change 無跨服務行為）。
- **Tier 未混列**：每列只有一個 Tier 值，無「unit + e2e」的混合列。
- **測試名稱與 spec 的「驗收」錨點逐字一致**：apply 收尾時 MUST 以腳本機械核對
  （比照 M2 tasks §13.1 的做法），不靠目視。
