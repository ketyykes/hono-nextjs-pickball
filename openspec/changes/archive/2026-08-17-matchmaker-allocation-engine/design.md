## Context

見 [proposal.md](./proposal.md) 的 Why。此處只記錄影響實作結構的現狀與約束。

- `lib/matchmaker/` 目前為**扁平佈局**（`types.ts`、`roster.ts`、`colors.ts`、`storage.ts`，各自鄰近一份 `*.test.ts`），本段沿用，不新增子目錄。
- `types.ts` 的 `Player` 已含 `rating`、`restCount`、`gamesPlayed`、`isActive`、`gender`，是 M1 為了避開破壞性遷移刻意預留的（見 `player-roster` spec「參賽者資料模型」）。本段**唯讀取用**，不改該檔。
- 本段輸出將由第 3 段（回合與對戰畫面）消費並持久化。因此輸出型別必須是**可序列化的純資料**，不得挾帶函式或 class 實例。
- 專案 `tsconfig.json` 開 `strict` 與 `verbatimModuleSyntax`，型別匯入須用 `import type`。

## Goals / Non-Goals

**Goals:**

- 把 `prd.md` 5.1 的嚴格優先序做成**可被單元測試逐條驗證**的結構——每一層取捨對應一個獨立函式，讓「後一項不得推翻前一項」成為函式呼叫順序上的必然，而非靠註解約束。
- 全段純函式、決定性、無 I/O，使第 3 段接上時不需要為了測試 UI 而 mock 分配邏輯。

**Non-Goals:**

- 不追求分配的**全域最優**。5.6 明講迴避是「盡量」，且限制條件（不得改名單、不得劣化強度）已使搜尋空間極小；引入最佳化求解器只會讓行為難以解釋。
- 不處理 `restCount` 累加、不建立回合物件、不碰持久化。
- 不做效能最佳化。PRD 12.1 的規模是 8～40 人，`O(n²)` 級的交換嘗試在此規模下遠低於一個 frame。

## Decisions

### Decision 1：拆成四個模組，而非單一 `allocation.ts`

| 模組 | 職責 | 對應 PRD |
|---|---|---|
| `allocation-types.ts` | 型別與常數（`MatchFormat`、`Team`、`Match`、`RoundAllocation`、預設值、場地數上下限） | 4.2、4.3、5.2 |
| `candidates.ts` | 候選排序、出場人數計算、出場／休息名單決策 | 4.3、5.3 |
| `pairing.ts` | 單打相鄰配對、雙打組隊、雙打組成標示 | 5.4、5.5 |
| `duplication.ts` | 三類簽章、重複偵測、受限交換 | 5.6 |
| `allocation.ts` | 串接上述四者的唯一對外入口 `allocateRound()` | 5.1 整體 |

理由是**優先序需要被結構強制**。單檔實作時，「強度配對不得更動出場名單」只能靠註解提醒；拆開後 `pairing.ts` 的簽章只接受「已決定的出場人員陣列」，它在型別上就拿不到休息名單，想違反也做不到。`duplication.ts` 同理——它只能重排既有 `Match[]`，無法新增或移除球員。

替代方案是單一檔案內用私有函式分層。否決理由：私有函式無法獨立測試，而 5.1 的四層取捨正是最需要逐層驗證的部分；且 M1 的經驗顯示，能被 spec 的 `驗收` 錨點直接指到的函式，`/opsx:verify` 才能機械核對。

### Decision 2：`allocation-types.ts` 為純型別檔，不寫單元測試

該檔只含 `export interface` / `export type` 與 `as const` 常數，無執行期邏輯、無函式。[`openspec/config.yaml`](../../config.yaml) 的 TDD 例外清單只列 `*.d.ts`、`next-env.d.ts`、`cloudflare-env.d.ts`，**不含**本檔——本檔免測的依據不是援引該清單，而是 config.yaml 主句「對……下所有**具備行為邏輯**的模組採通用 TDD」：本檔無函式，本來就不在 TDD 適用範圍內。

但**常數不是型別**——`DEFAULT_FORMAT`、`DEFAULT_COURT_COUNT`、`MIN_COURT_COUNT`、`MAX_COURT_COUNT` 有對外可觀察的值，spec 也為它們寫了 Scenario。這些常數的斷言掛在 `candidates.test.ts`（消費它們的模組），而不是為型別檔硬造一份測試檔。

### Decision 3：暫停出場者不列入休息名單

`prd.md` 5.3 寫「依上述排序取出該人數的人員出場，**其餘人員**進入休息名單並於本輪結束後休息次數 +1」。「其餘人員」的範圍是**候選池內**未被選中者；暫停者根本不在候選池，因此不列入。

這不只是文義解釋，也是行為上的必要選擇：若暫停者計入休息名單，第 3 段在回合結束時會替他們 `restCount + 1`。一個暫停三場的人恢復出場時 `restCount` 已比全場高出 3，會連續霸佔前幾輪的出場名額——而他這段期間根本沒有「等待上場」。這會讓一路在場的人反而被擠下去，與「休息次數多者優先」想解決的公平問題完全相反。

替代方案是計入休息名單但由第 3 段判斷不累加。否決理由：那把一個屬於分配語意的決定推給消費端，第 4、5 段若也消費此輸出就得各自重複同一條判斷。

### Decision 4：簽章元素用排序後的 id 串接；索引 in-memory 用 `Set`、持久化用陣列

三類簽章（隊友、交叉對手、完整比賽）的每一筆皆先對 player id 做 `LC_ALL` 無關的字典序排序再以分隔符串接成字串。理由是**簽章必須與排列順序無關**——同一組人換個位置列出就該視為同一組合，否則交換位置即可騙過重複偵測，5.6 的整段迴避形同虛設。

`SignatureIndex` 三個欄位的型別為 `ReadonlySet<string>`，而非陣列：**陣列允許重複條目，Set 天然去重**——型別名叫「索引」卻不保證唯一性是本末倒置，且第 3 段逐輪 append 時陣列會無界成長並被寫進 LocalStorage。Set 同時提供 O(1) 比對。「輸出須可序列化」的約束屬於**第 3 段要持久化的表示法**，不屬本段 in-memory 使用的 `AllocationInput`——`AllocationInput` 是 `allocateRound()` 的**函式引數**，不是持久化紀錄，套用「可序列化」這個約束套錯了對象。持久化仍以字串陣列表示（`Set` 無法被 `JSON.stringify` 直接還原成 `Set`），由第 3 段在讀取 LocalStorage 時把陣列轉換為 `Set`、寫回前把 `Set` 轉換回陣列；這道轉換屬於第 3 段的持久化邊界，不屬本段職責。

分隔符選 `|`（隊內）與 `#`（隊間），皆非 `crypto.randomUUID()` 產生的 id 會出現的字元，不會造成歧義。

### Decision 5：強度差距以「全場差距總和」衡量，而非單場

5.6 要求「不得使強度差距劣於調整前」。交換必然同時影響兩個場地，只看單場會出現「A 場變好、B 場變更差」卻通過檢查的情況。因此比較基準取**全場差距總和**：單打為每場雙方 `rating` 差的絕對值總和，雙打為每場兩隊 `rating` 總和差的絕對值總和。

判準為 `調整後總和 <= 調整前總和`（允許相等）。取 `<=` 而非 `<` 是刻意的：相等代表強度品質未劣化，此時若能減少重複就該接受——用 `<` 會讓大量「零成本」的迴避機會被白白放棄。

### Decision 6：交換採「試探並回退」，依 5.6 的三個階段依序進行

依 5.6 明列的順序：① 交換不同場地的球員 ② 交換隊伍內隊友 ③ 重新排列相鄰強度接近的候選人。每次試探先計算 `(重複數, 強度差距總和)`，只在**重複數下降且強度差距總和未增加**時採納，否則回退。

採貪婪逐步改善而非窮舉：8～40 人下窮舉所有交換組合是階乘級，而 5.6 本身只要求「盡量」迴避並明文允許接受重複。貪婪的結果**決定性**（無隨機、固定掃描順序），符合 spec 對「相同輸入產生相同輸出」的要求。

### Decision 7：場地數超出 1～8 時拋錯，不夾值

`prd.md` 4.3 定義範圍為 1～8，但未說超出時怎麼辦。選擇拋錯而非夾值，理由與 M1 對 `rating` 的處理一致（見 `player-roster` spec：「`rating` 超出範圍時 MUST 驗證失敗，SHALL NOT 靜默夾值」）——靜默夾值的失敗模式是**沉默的**：UI 的加號按鈕看起來沒反應，使用者不知道是撞到上限還是壞了。拋錯讓第 3 段能明確接住並顯示 PRD 第 11 節要求的繁體中文錯誤訊息。

UI 層的加減按鈕本來就該在邊界 disable，正常操作不會觸發此路徑；它防的是程式錯誤與未來從 LocalStorage 回讀損壞設定的情況。

### Decision 8：排序依賴 `Array.prototype.sort` 的穩定性

ES2019 起 `Array.prototype.sort` 保證穩定，`prd.md` 5.3 第 3 點的「維持穩定排序」因此不需要額外攜帶原始 index。專案 target 為現代瀏覽器（PRD 12.2），無需 polyfill。

排序前 MUST 先 `slice()` 複製——`sort` 原地修改，直接排會改到呼叫端的陣列，違反 spec 的「輸入的 `Player` 陣列 MUST 被視為唯讀」。

## Risks / Trade-offs

- **[貪婪交換可能錯過更好的解]** → 5.6 明文允許接受重複，且限制條件（不得改名單、不得劣化強度）已把可行解壓到很小。以「重複數是否下降」為驗收標準而非「重複數是否為 0」，避免規格承諾做不到的事。

- **[已知盲點：完全重複的雙打場次一步都動不了]** → `countRepeats` 回傳的是「**有命中的場次數**」而非「命中次數」。單次交換只能拆掉一支隊伍，另一支的隊友簽章仍然命中，於是場次數不變，而採納條件要求重複數**嚴格**下降，所有候選一律回退。

  code review 建構過實測反例：歷史為 `[m1,m4] vs [m2,m3]`（rating 8/2/5/5），現況 court1 同組、court2 為四位同分球員。存在一組零成本解（`repeats=0, spread=0`），但 `avoidRepeats` 原封不動回傳輸入（`repeats=1, spread=0`）。

  **這不違反 5.6**——該節只要求「盡量」迴避並明文允許接受重複，本 design 的 Non-Goals 也已放棄全域最優。記錄於此是為了讓日後看到「明明有更好的解卻沒採用」的人知道這是已知取捨，不必重查。若未來要改善，正確的方向是讓採納條件看「命中類別數」而非「場次數」，但那會改變 `countRepeats` 的公開語意，需另開 change。

- **[`doublesComposition` 在重複迴避後會失效]** → `duplication.ts` 只負責重排既有球員，不重新推導顯示用標示（職責邊界見 Decision 1）。但跨場地換人後，一場原本 4 人皆為 `male` 的比賽可能變成 3 男 1 女，標示卻仍停在男雙。

  code review 量化過可達性：3000 組隨機雙打情境中 `avoidRepeats` 改動了 99.7%，其中 **28%** 的「依實際 4 人重新推導的標示」與沿用的舊標示不同——每 3～4 場就有 1 場標錯。

  雖然 spec 明講此標示不參與任何決策，但錯的標示仍是使用者看得到的錯誤資料（PRD 13.3 驗收項有「可辨識男雙、女雙、混雙」）。**緩解方式**：`allocateRound` 在 `avoidRepeats` 之後重新呼叫 `labelDoublesComposition` 重算標示。這道重算是 `allocation.ts` 的整合責任，不下放給 `duplication.ts`——否則低順位的重複迴避模組會反向依賴配對模組，破壞 Decision 1 的單向依賴。

- **[「強度接近」缺乏絕對判準]** → 5.4／5.5 只說「盡量接近」。本段以**相對比較**寫測試（相鄰配對的分差總和不大於其他配對方式；雙打組隊方式的總和差不大於其餘兩種分隊），而非硬編一個閾值——閾值會在調色盤式的任意輸入下失效，相對比較則永遠成立。

- **[輸出型別將被第 3 段持久化，日後改型別即是破壞性遷移]** → 這是 M1 `restCount`／`gamesPlayed` 教訓的延續。本段的 `Match` 一次帶齊 5.2 列舉的全部欄位（場地編號、隊伍球員、隊伍分數、對戰類型、雙打組成標示），即使第 3 段暫時用不到某欄也先放進去。

- **[全員暫停時休息名單為空，UI 可能誤顯示為「沒有人」]** → 這是 Decision 3 的必然結果。第 3 段需要區分「名單為空」與「全員暫停」兩種空狀態並給不同文案；已在 spec 的邊界 Scenario 中把兩者拆成獨立情境，第 3 段接手時不會漏。
