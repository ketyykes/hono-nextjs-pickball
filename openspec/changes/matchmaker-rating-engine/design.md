## Context

見 [proposal.md](./proposal.md) 的 Why。此處只記錄影響實作結構的現狀與約束。

- `lib/matchmaker/` 為扁平佈局，第 1 段已新增 `allocation-types.ts`、`candidates.ts`、`pairing.ts`、`duplication.ts`、`allocation.ts`、`rating-math.ts`。本段沿用扁平佈局，只新增 `rating.ts`。
- `rating-math.ts` 的 `roundRating` 是第 1 段末為了消除兩處重複的四捨五入而抽出的共用函式，本段直接取用。
- `types.ts` 的 `Player` 已含 `rating`（1～8）與 `gamesPlayed`（非負整數，M1 只初始化不累加）。本段唯讀取用。
- **`prd.md` 6.4 有兩處內部衝突**，必須在本段解決並記錄，否則實作只能靠猜（見 Decision 1、2）。

## Goals / Non-Goals

**Goals:**

- 把 PRD 6.4 的每一條公式與常數做成**可被單元測試逐條驗證**的純函式，包含 6.4.2 表格裡那四個校準點。
- 讓 6.4.6 要求的「UI 需明確標示已達上限／下限」在**引擎層**就有可判讀的資料可用，而不是要 UI 自己從「分數沒變」去猜。

**Non-Goals:**

- 不處理 `gamesPlayed` 累加、不寫回 `Player`、不碰持久化與歷史紀錄。
- 不做效能最佳化。每場只算 2～4 個人，四則運算。
- 不提供「重算歷史」的能力。PRD 6.4.7 明講手動覆蓋「只影響之後的比賽，不重算既有歷史」，而本段無狀態，這件事自然成立。

## Decisions

### Decision 1：`K_eff` 取自該員自己的 `gamesPlayed`，不取隊伍平均

**這是 `prd.md` 的內部衝突，必須擇一。**

- 6.4.3 寫：`K_eff = K_base × (1 + 20 / (20 + **該員**累計出場次數))`，主詞明確是個人。
- 6.4.4 寫：雙打「同隊兩人各自加減**同一數值**」。

兩者在雙打時無法同時成立——同隊兩人 `gamesPlayed` 不同就會得到不同的 `K_eff`，變動的絕對值必然不同。

**採 6.4.3。** 理由：

1. 6.4.3 附有完整的設計目的說明——「讓主持人初始估錯的人在約 3 個活動夜內回到正確名次，同時使老手的分數不會因單場意外大幅跳動」。若取隊伍平均，一位新加入者只要跟老手同隊，`K_eff` 就被拉低，這個目的在雙打場合直接失效。而本產品的預設使用情境（8～40 人、多場地）雙打佔比很高。
2. 6.4.3 的主詞「該員」沒有解釋空間；6.4.4 的「同一數值」則可以合理讀成「同隊兩人共用同一個 `(S − E)`、同進同退」——那正是雙打的實際語意（兩人一起贏或一起輸，不會一個加一個減）。
3. 取平均會讓「我的分數變動取決於隊友打過幾場」，這比「不同人變動幅度不同」更難向使用者解釋。

替代方案是取隊伍平均 `gamesPlayed`。否決理由如上第 1 點——它讓 6.4.3 的整段理由在雙打中失效。

**此決定已寫進 delta spec 的 Requirement「雙打賽後更新」，並在該處引用本 Decision。**

### Decision 2：零和被 K 遞減與 clamp 破壞，記錄而不修補

6.4.5 宣稱「本模型為零和——一方增加多少，另一方即減少多少，群體總分守恆」。**這個敘述在 PRD 自己的其他條款下不普遍成立**，有兩個獨立的破壞來源：

**(a) K 依個人出場次數遞減（6.4.3）。** 單打 A 勝 B：`ΔA = K_A × (1 − E_A)`、`ΔB = −K_B × (1 − E_A)`。兩者相等的充要條件是 `K_A = K_B`，即雙方 `gamesPlayed` 相同。這與 clamp 無關，是 6.4.3 與 6.4.5 的直接衝突。

**(b) clamp（6.4.6）。** 8.00 的人獲勝加不了分，對手卻照常扣分，群體總分下降。

**採「照 6.4.3 與 6.4.6 執行，讓偏離可被觀測」。** 不為了守恆而扭曲任一方的變動量——例如把敗方的扣分綁到勝方的實際加分。那會讓「我輸掉這場扣幾分」取決於對手是不是剛好卡在 8.00，無法向使用者解釋，而且會讓分配演算法依賴的相對差距出現不可預測的跳動。

6.4.5 的真正用意是說明「這個分數不是 DUPR、不能對外宣稱」——這個結論不受守恆是否成立影響，仍然完全正確。因此本段把 6.4.5 解讀為**語意宣告**（相對值、不可對外）而非**數學保證**（嚴格守恆），並在 delta spec 中明列守恆成立的三個條件。

### Decision 3：輸入為「勝方球員陣列 + 敗方球員陣列」，不吃 `Match`

`rating.ts` 的入口接受 `{ winners: readonly Player[]; losers: readonly Player[] }`，而非 `match-allocation` 的 `Match` 加上勝方索引。

理由是**避免兩個 capability 互相耦合**。評分與分配是兩件獨立的事——PRD 6.3 明講比分可以來自 `/scoreboard` 或手動輸入，第 3 段甚至可能為「臨時換人代打」的場次計分。若 `rating.ts` 只吃 `Match`，這些路徑都得先偽造一個 `Match` 才能評分。

另外 `Team.rating` 是**總和**而非平均（第 1 段的定義），若直接取用容易誤把總和餵進以平均校準的 `D = 3.0`，使分差放大一倍。改吃球員陣列後，平均在本段內自行計算，不存在誤用空間。

第 3 段從 `Match` + 勝方索引轉成本段的輸入只是兩行解構，成本遠低於耦合的代價。

### Decision 4：回傳 clamp 前的理論變動量與撞邊界標記

每筆變動回傳 `{ playerId, before, after, delta, rawDelta, clamped }`：

- `delta` 是**實際生效**的變動（`after − before`，clamp 後）
- `rawDelta` 是 clamp **前**的理論變動
- `clamped` 為 `"none" | "at-max" | "at-min"`

只回 `after` 是不夠的。PRD 6.4.6 要求 UI 標示「已達上限／下限」且「不得靜默卡住讓使用者誤以為功能故障」——但 UI 從「分數沒變」單獨無法分辨「撞到邊界」與「計算結果剛好為零」（勢均力敵時 `S − E` 可能極小，四捨五入後 `delta` 為 0）。用一個明確的列舉標記，UI 不需要重算任何東西就能決定要不要顯示提示。

`rawDelta` 則讓「差多少才會超出」這類資訊在需要時可得，且是 Decision 2 中「讓偏離可被觀測」的具體載體。

### Decision 5：四捨五入只在最終寫入點做一次

`E`、`K_eff`、`S − E` 的中間結果**不**四捨五入，只有 `after` 經 `roundRating` 取兩位小數。

中間值取整會讓誤差在公式內逐級放大——`E` 只取兩位小數時，`0.5948` 變 `0.59`，單場變動就偏掉約 1%。而 `after` 必須取整，因為 `Player.rating` 的精度就是兩位小數（`player-roster` spec 明列），不取整會把浮點尾數寫進 LocalStorage。

這與第 1 段 `roundRating` 的用法一致：`buildTeam` 也是只在產出 `Team.rating` 時 round 一次。

順帶說明：`delta = after − before` 是**在 round 之後**計算的，因此 `delta` 必然是兩位小數的差；`rawDelta` 則保留完整精度。這讓「delta 加總是否守恆」的檢查建立在實際生效的數字上，而不是理論值。

## Risks / Trade-offs

- **[Decision 1 讓同隊兩人變動幅度不同，可能被使用者視為不公]** → 這是 6.4.3 的必然代價，且方向是對的（新手收斂快）。第 3 段的 UI 若要顯示變動量，應同時顯示「新手加速中」之類的說明，而非讓使用者自行推測。已在此記錄，避免第 3 段把它當成 bug 回報。

- **[Decision 2 使群體總分會緩慢漂移]** → 長期而言，撞上限的贏家與 K 較大的新手會讓總分緩慢下降或上升。因為分配演算法只依賴**排序與相對差距**（PRD 6.4.5 自己也這樣寫），漂移不影響分配品質。真正要避免的是 UI 把絕對值當等級展示——那是 spec 的 Purpose 已明文禁止的事。

- **[`K_eff` 恆大於 `K_base`，PRD 6.4.2 的「±0.075」永遠達不到]** → `K_eff = K_base × (1 + 20/(20 + n))` 在任何有限 `n` 下都大於 `K_base`，所以「勢均力敵時單場變動 ±0.075」是**極限值**而非實際值（`n = 100` 時仍為 0.0863）。spec 的 Scenario 因此寫成「趨近」而非「等於」，避免測試用一個永遠達不到的數字當斷言。

- **[`gamesPlayed` 由第 3 段累加，本段拿到的可能是「賽前」或「賽後」的值]** → 本段的契約是**賽前值**（該員在這場之前打過幾場）。若第 3 段先累加再呼叫評分，新手的第一場就會用 `n = 1` 而非 `n = 0`，K 少了 2.4%。差異不大但會讓測試對不上規格數字。已在 spec 的 Requirement「無狀態與決定性」中明列本段只讀取不累加，第 3 段接手時應先評分後累加。
