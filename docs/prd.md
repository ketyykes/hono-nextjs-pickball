## 1. 產品概述

「匹克球對戰分配機」是一個以瀏覽器運作的匹克球對戰管理工具。使用者可以建立參賽者名單、設定個人性別與雙色漸層標記、維護匹克球強度分數，並依單打或雙打、場地數量與上一輪對戰紀錄，自動產生新的對戰組合。

系統以 Elo-based 強度分數作為主要分配依據，同時納入累計休息次數與重複配對迴避，讓出場機會與對戰強度更平衡。對戰畫面不採一般列表卡片，而是以「滿版方型色塊」呈現球員位置：單打顯示兩個 1x1 球員色塊；雙打顯示四個 1x1 球員色塊組成 2x2 場地視覺。

本版所有名單、回合、比分與歷史紀錄都保存在目前瀏覽器的 LocalStorage，不上傳任何後端。使用者可將資料匯出或匯入，以便備份與跨裝置搬移。

| 目標 | 成功條件 |

## 3. 使用者與使用情境

### 3.1 主要使用者

主要使用者為球聚主持人、社團幹部、教練或負責現場分配對戰的人員。使用者通常需要在手機或平板上快速操作，也可能在桌面瀏覽器上事前建立名單與整理歷史。

### 3.2 典型使用流程

1. 開啟 App，首次使用時顯示空白參賽者名單，不得自動帶入任何假資料。
2. 新增參賽者，輸入姓名、性別、雙色漸層與強度分數。
3. 將暫時不出場的人員切換為暫停狀態。
4. 選擇單打／雙打與場地數。
5. 按下「產生本輪對戰」。
6. 依場地查看滿版色塊對戰資訊與休息名單。
7. 比賽結束後輸入兩隊比分並送出。
8. 系統更新 Elo 分數，將比賽移入本輪已完成區域並新增歷史紀錄。
9. 需要新一輪時，保留既有重複配對基準並重新分配尚未完成場次。
10. 活動結束後可匯出 JSON／CSV／JPG／PDF 備份。

## 4. 功能需求

### 4.1 參賽者管理

使用者可以新增、編輯、刪除參賽者。每位參賽者需具備以下資料：

| 欄位 | 必填 | 規格 |
|---|---:|---|
| 參賽者名稱 | 是 | 不可為空白 |
| 性別 | 是 | 男、女、其他／不指定 |
| 顏色起點 | 是 | Hex 色碼，例如 `#0E6B63` |
| 顏色終點 | 是 | Hex 色碼，例如 `#58A99A` |
| 強度分數 | 是 | 1.00～8.00，可輸入小數點後兩位。初始由使用者設定，之後由系統依比賽結果更新（見 6.4），使用者仍可隨時手動覆蓋 |
| 累計休息次數 | 系統 | 初始為 0，每輪未被分配到場次時 +1；用於出場排序（多者優先） |
| 累計出場次數 | 系統 | 初始為 0，每完成一場 +1；用於評分更新的信賴度加權（見 6.4） |
| 出場狀態 | 是 | 出場中／暫停出場 |
| 建立時間 | 系統 | ISO 8601 時間 |

#### 4.1.1 顏色標記

參賽者可自訂雙色 Hex 漸層。系統在名單頁、對戰舞台與匯出圖片中使用相同漸層，讓使用者可快速辨識球場位置。文字顏色需依背景亮度自動選擇深色或淺色，以維持可讀性。

#### 4.1.2 暫停出場

參賽者切換為「暫停出場」後，不得被納入下一輪對戰候選池，也不得因本輪休息而增加休息次數。恢復為「出場中」後，才可參與下一輪分配。

#### 4.1.3 快速帶入強度

| 級別 | 分數 |
|---|---:|
| 新手 | 1.00 |
| 中階 | 3.00 |
| 高階 | 5.00 |

使用者仍可手動輸入 1.00～8.00 範圍內、小數點後兩位的分數。

#### 4.1.4 初始名單

首次開啟 App 時，參賽者名單必須為空白。系統不得自動帶入假姓名、假分數、假賽程或假歷史。若瀏覽器內留有舊版示範種子資料，更新後應一次性清除，不影響使用者自行建立的資料。

#### 4.1.5 重置參賽者名單

參賽者頁提供「重置名單」按鈕。按下後必須顯示明確確認提示：

> 確定要重置參賽者名單嗎？這會清除全部參賽者、目前回合與歷史賽果，且無法復原。

使用者確認後，系統清除全部參賽者、進行中的回合、歷史賽果與相關本機資料，回到空白初始狀態。使用者取消時不得改變任何資料。

### 4.2 對戰方式設定

提供以下模式：

| 對戰方式 | 說明 |
|---|---|
| 單打 | 每場 2 位參賽者；畫面為兩個 1x1 色塊 |
| 雙打 | 每場 4 位參賽者；畫面為 2x2 色塊 |

> **不做性別限定模式**：本產品不提供「僅混雙／僅男雙／僅女雙」這類以性別篩選出場人選的模式。
> 性別欄位只用於顯示與雙打組成的事後標示（見 5.5），**不影響任何人的出場機會**。
> 這讓分配演算法只需維護單一候選池，「休息次數多者優先」不存在任何例外。

### 4.3 場地數

場地數控制項預設為 **1**。使用者可用加減按鈕調整場地數，範圍為 1～8 個場地。產生對戰時，系統依場地數計算本輪最多可容納的對戰數。

若可用人數不足以填滿所有場地，系統只產生可完整組成的場次，剩餘人員列入休息名單。

## 5. 對戰分配演算法

### 5.1 分配優先序

分配決策採**嚴格優先序**，順序為：

> **模式結構性約束 ＞ 累計休息次數 ＞ 強度接近 ＞ 重複配對迴避**

前一項永遠不得為了滿足後一項而讓步：

0. **模式的結構性約束（最硬）**：每場人數必須整除（單打 2 人、雙打 4 人）。此約束無法被任何後續項目推翻。
1. **累計休息次數（次高）**：休息次數**多**者一定優先出場，**無任何例外**——性別不構成篩選條件。不得為了平衡強度、也不得為了避開重複配對，而讓休息次數較多的人繼續休息。出場人選一旦依此決定，後續步驟不得更動。
2. **強度接近（第三）**：在不改變出場人選的前提下，讓對戰雙方分數盡量接近——單打採相鄰配對，雙打以隊伍總和平衡。
3. **重複配對迴避（最低）**：只在不違反第 0、1、2 項的前提下嘗試調整。若任何可行的調整都會改變出場人選，或使強度差距劣於調整前，則放棄迴避、接受重複。

四者衝突時一律依此順序取捨，且任何情況下都不得產生不完整隊伍。

> **為何休息次數是「多者優先」**：休息次數少代表已經打了很多場，若讓他繼續優先出場會形成死鎖——
> 出場者休息次數不增加，於是永遠是同一批人上場，其餘人永遠等不到。
> 改為多者優先後，出場機會會自然輪轉。

### 5.2 輸入與輸出

輸入包含目前出場中的參賽者、強度分數、對戰方式、場地數、累計休息次數與上一輪對戰組合。輸出包含 N 組對戰、場地編號、隊伍球員、隊伍分數、對戰類型與休息名單。

### 5.3 候選排序

候選人員依以下順序排序：

1. 累計休息次數**多**者優先。
2. 同休息次數時，依強度分數高者優先。
3. 若仍相同，維持穩定排序，避免每次產生結果大幅跳動。

系統依對戰方式及場地數計算本輪出場人數：

```
出場人數 = min(可用人數, 場地數 × 每場人數)  並向下取整至每場人數的倍數
```

依上述排序取出該人數的人員出場，其餘人員進入休息名單並於本輪結束後休息次數 +1。**此步驟決定的出場／休息名單即為最終結果**，後續的強度配對與重複迴避都不得再更動名單成員。候選池只有一個，不因性別分池。

### 5.4 單打

1. 取用 5.3 已決定的出場人員（人數必為偶數，奇數人的排除在 5.3 完成）。
2. 依強度分數排序。
3. 相鄰兩兩配對，使對戰雙方分數差距盡量接近。
4. 每場包含 2 個球員 1x1 色塊。

### 5.5 雙打

1. 取用 5.3 已決定的出場人員（人數必為 4 的倍數，不足 4 人的尾端在 5.3 已排除）。
2. 依強度分數由高到低排序。
3. 每 4 人形成一個候選組。
4. 組內以「最高＋最低」形成第一隊。
5. 以「第 2 高＋第 3 高」形成第二隊。
6. 以兩隊平均或總和分數判斷隊伍平衡。
7. 每場包含 4 個球員 1x1 色塊，排列為 2x2。
8. 依組內性別**事後標示**男雙、女雙或混雙；含「其他／不指定」而無法歸類時標示為一般雙打。此標示純為顯示用途，**不參與任何選人或配對決策**。

### 5.6 避免重複對戰

重複配對迴避是分配優先序中的**最低順位**，只能在出場名單與強度配對都已決定之後執行。

系統需記錄同隊隊友組合、兩隊交叉對手組合、完整比賽組合、本輪已完成及進行中的場次，以及重設前的原始對戰組合。

產生新一輪後，若偵測到重複，依序嘗試交換不同場地的球員、交換隊伍內隊友、重新排列相鄰強度接近的候選人。所有調整都必須滿足以下限制：

- **不得改變出場與休息名單的成員**。不可為了避開重複而把已入選者換成休息名單中的人，也不可讓休息次數較多者繼續休息。
- **不得使強度差距劣於調整前**。單打以雙方分數差、雙打以兩隊總和差衡量；若所有可行交換都會讓差距變大，則保留原配對並接受重複。
- 不得因此產生不完整隊伍。

在候選人數過少、或上述限制使得無交換可行時，直接接受重複並照常產生對戰，不得因為無法避開重複而不產生場次或跳過任何應出場的人。

## 6. 回合與比分管理

### 6.1 產生本輪對戰

按下「產生本輪對戰」後，系統依目前設定建立新回合。若已有上一輪，上一輪的所有已完成與進行中組合都納入重複比對基準。每輪需保存回合編號、建立時間、對戰方式、場地、對戰清單、休息名單與賽前分數。

### 6.2 重設／重排本輪

只有在目前回合存在且仍有未完成場次時，才顯示「重設／再排」或「重排未完成」操作。重設需保留已完成場次、比分及 Elo 更新結果，只重新分配尚未比賽的參賽者，並沿用原本回合與前一輪的重複配對基準。

### 6.3 比分來源

每場對戰有兩種完成方式，兩者產生相同的後續結果（記錄最終比分 → 更新評分 → 寫入歷史）：

| 方式 | 說明 |
|---|---|
| **場邊計分** | 由該場對戰進入既有的 `/scoreboard` 計分板，依 2026 USA Pickleball Traditional（side-out）規則逐球計分，勝負底定後回填 |
| **手動輸入** | 直接在場地區塊填入兩隊最終比分並送出 |

手動輸入為必要的 fallback，不得移除：主持人可能在其他工具計分、臨時換人代打，或於賽後補登。

#### 6.3.1 與計分板的銜接

- **目標分數（11／15／21）為每輪設定**，同一輪的所有場地共用，於「產生本輪對戰」時決定；該輪一旦有場次開始計分即不可更改。
- 計分板狀態必須與**特定對戰場次**綁定。現行 `scoreboard:current:v1` 為全站單一場次，接上分配機後需改為可識別所屬對戰，否則多場地同時進行時會互相覆蓋。
- 由計分板返回時：若該場已判定勝負，最終比分自動回填該場次；若尚未結束，保留計分進度，可再次進入接續計分。
- 計分板既有的 Undo、全螢幕、專注模式等行為不因接入而改變。

#### 6.3.2 比分驗證

每場提供兩個比分欄位，分別代表第一隊與第二隊。比分必須為非負數字。

以下情況不得送出：

- 任一欄位未填寫。
- 任一欄位不是有效數字。
- 兩隊比分相同，即平局。
- 場次已完成。

### 6.4 評分更新

送出比分後，系統更新雙方評分。採 Elo 架構，但**常數依 1.00～8.00 的尺度重新校準**——標準 Elo 的 `D=400`、`K=32` 是為西洋棋的 1500 分級距設計，直接套用在全距只有 7 的尺度上，會使預測勝率退化為約 51%（毫無鑑別度），且單場變動達 ±15 分，一場即撞頂。

#### 6.4.1 公式

```
預測勝率   E = 1 / (1 + 10^(-(Ra - Rb) / D))
賽後更新   Ra' = Ra + K_eff × (S - E)          S：勝 = 1，敗 = 0
```

#### 6.4.2 常數

| 常數 | 值 | 效果 |
|---|---:|---|
| `D`（級距） | **3.0** | 分差 0.5 → 強者勝率 60%；1.0 → 68%；2.0 → 82%；3.0 → 91% |
| `K_base`（基礎幅度） | **0.15** | 勢均力敵時單場變動 ±0.075 |

#### 6.4.3 K 依出場次數遞減

```
K_eff = K_base × (1 + 20 / (20 + 該員累計出場次數))
```

新加入者（0 場）K 為 2 倍，可快速定位到合理區間；累計 20 場時降為 1.5 倍；長期趨近 `K_base` 而趨於穩定。此設計讓主持人初始估錯的人在約 3 個活動夜內回到正確名次，同時使老手的分數不會因單場意外大幅跳動。

#### 6.4.4 雙打

以兩隊的**平均分數**計算 `E`，同隊兩人各自加減同一數值。

#### 6.4.5 評分為相對值

本模型為零和——一方增加多少，另一方即減少多少，群體總分守恆。因此評分只保證**群體內的相對排序與相對差距**，其絕對值不對應 DUPR 或任何外部等級制度，也不會因為某人變強而使全體平均上升。

分配演算法只依賴排序與相對差距，此特性不影響分配品質；但 UI **不得**將此分數標示為對外通用的技術等級。

#### 6.4.6 邊界處理

更新後的分數 clamp 於 1.00～8.00。已達上限或下限者仍照常參與計算與配對，但分數不再變動；UI 需明確標示「已達上限／下限」，不得靜默卡住讓使用者誤以為功能故障。

#### 6.4.7 手動覆蓋

使用者可隨時在參賽者頁直接編輯強度分數，覆蓋系統計算結果。覆蓋只影響之後的比賽，不重算既有歷史。

### 6.5 完成場次

完成的場次自動標示為已完成，顯示最終比分、勝方與完成時間，並以半透明、低飽和度樣式呈現。已完成場次不得再次送出相同比分。

## 7. 對戰畫面與視覺規格

### 7.1 核心原則

對戰頁不得使用附圖所示的傳統垂直卡片列表作為主要對戰呈現。每個場地應以具有球場感的方型滿版視覺區塊呈現，讓球員色彩成為現場辨識主體。

### 7.2 單打

單打每場顯示兩個 1x1 方型色塊，左右排列。每格顯示姓名、性別與強度分數，背景使用參賽者自訂雙色漸層。比分輸入區位於色塊下方或下緣 Overlay 區域。

### 7.3 雙打

雙打每場顯示四個 1x1 方型色塊，排列為 2x2。對角或左右兩格代表同一隊，中央或下方顯示隊伍比分與送出控制。不得將雙打縮小成一般列表卡片。

### 7.4 休息名單

休息名單需顯示在場次頁的輔助區域，至少包含姓名、顏色標記及目前累計休息次數。桌面版可位於對戰舞台右側；手機版可移至對戰內容下方。

### 7.5 空白狀態

首次開啟或重置後，場次頁顯示空白球場狀態，不得顯示假名單。畫面應提供「建立第一輪」或導向「加入參賽者」的操作入口。

### 7.6 響應式

| 裝置 | 規格 |
|---|---|
| 桌面 | 左側導覽、中央場地內容、右側休息名單 |
| 平板 | 場地內容優先，休息名單可移至下方 |
| 手機 | 底部導覽；色塊、比分輸入與按鈕需適合觸控 |

## 8. 歷史紀錄

### 8.1 時間區間定義

歷史頁提供五個區間。區間**必須互斥且完整覆蓋**所有時間，不得出現任何一筆賽果落不進任何區間的情況。

定義方式為：先由近至遠計算四個切點，再以相鄰切點框出區間。切點一律取當地時區的 00:00，週起始為**週一**。

```
C0 = 今天 00:00
C1 = min(本週一 00:00, C0)
C2 = min(當月 1 日 00:00, C1)
C3 = min(上月 1 日 00:00, C2)
```

| 篩選 | 範圍 |
|---|---|
| 今日 | `[C0, 現在]` |
| 本週 | `[C1, C0)` |
| 本月 | `[C2, C1)` |
| 上月 | `[C3, C2)` |
| 更早 | `(-∞, C3)` |

`min()` 是關鍵：它保證切點單調不遞增，區間因此永不重疊，跨月的那一週也會自動落入正確歸屬（該情況下「本月」為空區間）。

**驗算一：一般情形（今天為 2026-08-15 週六）**

```
C0 = 8/15   C1 = 8/10   C2 = 8/1   C3 = 7/1

今日  8/15          本週  8/10 ~ 8/14
本月  8/1 ~ 8/9     上月  7/1 ~ 7/31      更早  7/1 之前
                    ↑
        此段在舊定義（「當月月初至上週一之前」）下無人認領
```

**驗算二：跨月週（今天為 2026-08-01 週六，本週一落在 7/27）**

```
C0 = 8/1   C1 = 7/27   C2 = min(8/1, 7/27) = 7/27   C3 = 7/1

今日  8/1            本週  7/27 ~ 7/31
本月  空區間         上月  7/1 ~ 7/26       更早  7/1 之前
      ↑
   當月 1 日就是今天，本月自然無內容——不是錯誤
```

### 8.2 紀錄欄位

每筆歷史至少包含：對戰 ID、場地、對戰時間、對戰方式、雙打組成標示、第一隊、第二隊、比分、勝方、賽前分數與賽後分數。空區間需顯示友善空白狀態。

## 9. 資料保存與匯入匯出

本版資料層只有瀏覽器 LocalStorage，不含任何後端儲存、帳號或跨裝置同步。跨裝置搬移一律透過匯出／匯入檔案完成。

### 9.1 LocalStorage

系統以瀏覽器 LocalStorage 保存參賽者名單、出場狀態、強度分數、累計休息次數、目前回合、已完成比賽、歷史賽果與重複配對簽章。首次啟動不得寫入假資料；重置後資料應回到空白初始狀態。

### 9.2 JSON

JSON 為完整備份格式，需包含版本號、參賽者、目前回合、歷史與重複配對資訊。匯入 JSON 時需驗證資料結構；格式錯誤不得覆蓋目前資料。

### 9.3 CSV

**CSV 的匯出與匯入處理的是不同的東西，兩者刻意不對稱，不構成 round-trip。** 需要完整還原請一律使用 JSON（9.2）。

```
   CSV 匯出  ───▶  歷史賽果      （拿去試算表看統計、貼進群組）
   CSV 匯入  ◀───  參賽者名單    （從 Google Sheet 把整團人一次貼進來）
```

會這樣拆，是因為「匯入歷史賽果」在語意上無解：那些賽果的參賽者若不存在該不該自動建立？評分要不要照歷史重算一次？賽前／賽後分數以檔案為準還是重算為準？任一個答案都會製造出與現況矛盾的資料。JSON 已經完整覆蓋備份還原的需求，CSV 不需要重複承擔。

#### 9.3.1 CSV 匯出（歷史賽果）

至少包含：日期、時間、對戰方式、雙打組成標示、場地、第一隊球員、第二隊球員、比分、勝方、各員賽前分數與賽後分數。編碼需可被 Excel 與 Google Sheets 正確辨識中文。

#### 9.3.2 CSV 匯入（參賽者名單）

| 欄位 | 必填 | 說明 |
|---|---:|---|
| 名稱 | 是 | 不可為空白 |
| 性別 | 是 | 男／女／其他，需接受常見寫法 |
| 強度分數 | 是 | 1.00～8.00 |
| 顏色起點 | 否 | 未提供時由系統自動配色 |
| 顏色終點 | 否 | 未提供時由系統自動配色 |

匯入行為：

- 匯入前需顯示**預覽**（將新增幾人、哪幾列有問題），使用者確認後才寫入。
- 第一版採**附加**模式：匯入的人一律新增，不覆蓋既有參賽者。
- **同名視為不同人**——球聚常有同名同姓，靜默合併的風險高於重複建立。重複匯入造成的重複人員由使用者自行刪除。
- 任一列驗證失敗時，需指出**是第幾列、哪個欄位、為什麼**，且**整份不匯入**，不得只匯入通過的部分而留下半套資料。

### 9.4 JPG

JPG 匯出目前場次畫面，需保留 App 名稱、回合編號、對戰方式、場地編號、球員色塊、姓名與比分或未完成狀態。

### 9.5 PDF

PDF 可採瀏覽器列印流程，內容需包含目前回合與各場次對戰資訊。若瀏覽器阻擋列印視窗，需提示使用者開啟彈出視窗權限。

## 10. 清除與重置規則

| 操作 | 清除內容 | 是否確認 |
|---|---|---:|
| 刪除單一參賽者 | 指定參賽者 | 是 |
| 重置名單 | 全部參賽者、目前回合、歷史賽果 | 是 |
| 清除本機資料 | 全部 LocalStorage 資料 | 是 |
| 取消操作 | 不更動任何資料 | 不適用 |

重置提示必須明確告知資料無法復原，並建議使用者先匯出 JSON 備份。重置完成後，參賽者頁與場次頁均需呈現空白狀態。

## 11. 錯誤處理與邊界條件

系統至少需處理以下狀況：

- 參賽者人數不足以產生單打。
- 雙打人數不足 4 人。
- 所有參賽者皆暫停出場。
- 比分欄位空白、非數字或平局。
- 匯入檔案格式錯誤。
- LocalStorage 內容損壞。
- LocalStorage 不可用或寫入超出配額。
- Hex 色碼不合法。
- 強度分數超出 1.00～8.00 範圍。
- 評分更新後撞到 1.00 或 8.00 邊界。
- 新回合無法完全避免重複。
- 重置後沒有任何參賽者。
- 由計分板返回時該場次已被刪除或該輪已重設。

錯誤訊息需使用繁體中文，並說明可採取的修正方式，不得只顯示技術錯誤碼。

## 12. 非功能需求

### 12.1 效能

主要使用規模為 8～40 位參賽者。產生對戰、送出比分與切換頁面應在一般裝置上即時完成。

### 12.2 相容性

支援現代 Chromium、Safari、Firefox 與行動瀏覽器。App 以線上網頁形式發布，載入頁面需要網路連線；頁面載入後的核心操作（維護名單、產生對戰、輸入比分、查看歷史）皆在本機完成，不呼叫後端 API。

### 12.3 可用性

主要按鈕需具備清楚的 hover、focus 與 disabled 狀態。比分欄位需支援手機數字鍵盤。所有功能不得只依賴滑鼠操作。

### 12.4 資料安全

本版不傳送參賽者資料至後端。所有資料只保存在使用者目前瀏覽器的 LocalStorage，使用者需自行透過 JSON 匯出進行備份。清除瀏覽器資料或更換裝置會導致資料遺失，介面需在重置與清除流程提醒此風險。

### 12.5 無障礙

色彩不可作為唯一資訊來源，場地與球員仍需顯示姓名與隊伍標籤。互動控制需具備可辨識的文字或 aria-label。

## 13. 驗收標準

### 13.1 初始資料

- [ ] 首次開啟時參賽者名單為空。
- [ ] 不顯示任何假姓名、假分數或假歷史。
- [ ] 既有舊版假資料能被一次性清除。（N/A——見 openspec/specs/player-roster/spec.md「空白初始狀態」：本 capability 為全新，瀏覽器內不存在舊版種子資料，無清除對象）
- [ ] 空白狀態提供加入參賽者入口。

### 13.2 參賽者

- [ ] 可新增、編輯、刪除參賽者。
- [ ] 可設定姓名、性別與自訂 Hex 雙色漸層。
- [ ] 可設定 1.00～8.00 的強度分數。
- [ ] 可使用新手／中階／高階快速分數。
- [ ] 可暫停與恢復出場。
- [ ] 點擊「重置名單」後會先顯示確認提示。
- [ ] 確認重置後全部參賽者、目前回合與歷史賽果均被清除。
- [ ] 取消重置後資料保持不變。

### 13.3 對戰

- [ ] 對戰方式預設為單打。
- [ ] 場地數預設為 1。
- [ ] 可調整場地數 1～8。
- [ ] 單打每場顯示兩個 1x1 滿版色塊。
- [ ] 雙打每場顯示四個 1x1 色塊組成 2x2。
- [ ] 暫停中的參賽者不會被分配。
- [ ] 休息次數**多**者優先出場。
- [ ] 連續多輪產生對戰後，出場機會會輪轉，不會固定由同一批人出場。
- [ ] 分數接近者優先配對。
- [ ] 雙打隊伍分數盡量平衡。
- [ ] 可辨識男雙、女雙、混雙（事後標示，不影響選人）。
- [ ] 性別在任何情況下都不影響出場順序：休息次數多者必定優先出場。
- [ ] 系統會檢查並盡量避免重複隊友與對手。
- [ ] 當避免重複會改變出場人選時，系統選擇接受重複，休息次數多者仍必定出場。
- [ ] 當避免重複會擴大強度差距時，系統保留原配對並接受重複。

### 13.4 比分與歷史

- [ ] 空白比分不得送出。
- [ ] 非數字比分不得送出。
- [ ] 平局不得送出。
- [ ] 可由對戰進入 `/scoreboard` 計分，勝負底定後比分自動回填。
- [ ] 多場地同時計分時，各場進度互不覆蓋。
- [ ] 未完成的計分進度可離開後再進入接續。
- [ ] 手動輸入比分的路徑仍可獨立完成一場。
- [ ] 送出後依 `D=3`、`K_base=0.15` 更新雙方評分，且不超出 1.00～8.00。
- [ ] 出場次數少者的評分變動幅度大於出場次數多者（K 遞減生效）。
- [ ] 爆冷獲勝者的加分明顯大於預期內獲勝者。
- [ ] 分數達 1.00 或 8.00 時 UI 標示已達上下限。
- [ ] 完成場次顯示最終比分並進入完成狀態。
- [ ] 歷史紀錄包含賽前／賽後分數、比分、勝方、模式與時間。
- [ ] 可依今日、本週、本月、上月、更早篩選歷史。

### 13.5 資料工具

- [ ] LocalStorage 可在重新整理後還原資料。
- [ ] 可匯出 JSON（完整備份）、CSV（歷史賽果）、JPG 與 PDF。
- [ ] 可匯入 JSON 完整還原。
- [ ] 可匯入 CSV 參賽者名單，並在寫入前顯示預覽。
- [ ] CSV 任一列驗證失敗時整份不匯入，且錯誤訊息指出列號與欄位。
- [ ] 錯誤檔案不得覆蓋原資料。
- [ ] 五個歷史區間互斥且完整覆蓋，任何一筆賽果都必定落在其中之一。
- [ ] 本週一落在上個月時，該週賽果歸入「本週」，「本月」顯示空狀態而非錯誤。

## 14. 後續版本方向

本節只記錄一件事：**資料層由 LocalStorage 改為線上版**。除此之外不列任何候選功能。

本版先做 LocalStorage，資料只存在使用者當下的瀏覽器。下一階段將改為線上帳號與雲端儲存，讓同一份名單、回合與歷史可跨裝置存取。屆時需處理的至少包含：登入方式、既有 LocalStorage 資料的遷移路徑，以及遷移後 LocalStorage 的定位（完全取代或作為離線快取）。這些細節待該階段另立文件，不在本 PRD 範圍。

產品形態仍只走線上網頁版，不評估原生 App、離線封裝或桌面應用。
